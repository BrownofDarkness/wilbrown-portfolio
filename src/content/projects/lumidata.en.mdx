Lumidata.ai is a data analytics platform built at IBAASS Labs. When I joined the team in January 2024, the environment was a patchwork of services running on laptops, improvised network shares, and exposed services with no clear hygiene. The mission: rebuild a complete, secure infrastructure — a cloud edge, a virtualized internal LAN, and all the surrounding tooling (SSO, VPN, observability).

## Context

The team was working on a fast-moving data product. Every dev had their own local instance, their own SSH tunnels to reach staging services, and nobody knew exactly which version of which dependency was running where. The cost: 2-3 hours lost every week to environment setup, recurring "works on my machine" bugs, and tangible security risk (services exposed in plaintext on the office network).

The goal was to lay the foundations of a two-tier infrastructure: a **public-facing cloud edge** handling SSL/SSO/VPN, and a **virtualized internal network** hosting the application stack — with strict isolation between the two.

## Architecture

I designed a **dual-network architecture**:

**Edge side, on AWS** — an **EC2 Ubuntu LTS** instance plays three roles:

- SSL termination through **Nginx** with auto-renewed **Let's Encrypt** certificates
- **SSO authentication** via **Pritunl Zero** for every internal service
- **OpenVPN endpoint** managed through **Pritunl VPN** (MongoDB backend)

**LAN side, on VMware ESXi** (internal bare-metal server) — 9 Ubuntu VMs provisioned with distinct roles:

- 1 **jumper VM** bridging the encrypted VPN network and the VMware LAN — strict isolation
- 1 **Nginx load balancer** in front of the application layer
- 1 **frontend** serving the SPA
- 1 **backend** exposing the APIs
- 3 **Elasticsearch nodes** clustered for search/indexing
- 1 **Kibana** for visualization
- 1 **APM Server** for application tracing

The user flow: HTTPS connection to the AWS edge → Pritunl Zero SSO auth → VPN tunnel to the jumper → routing into the internal LAN. The internal network is never exposed directly to the Internet — only the edge is.

## Outcomes

- **AWS edge operational**: automated SSL + unified SSO + VPN endpoint
- **9 ESXi VMs in production** on the internal LAN, each with a clear role and runbook
- **3-node Elasticsearch cluster** running for search/indexing
- **Kibana + APM Server observability stack** deployed
- **Unified Pritunl Zero SSO** — one login across all internal services
- **AES-128-GCM encrypted VPN tunnel** for LAN access without Internet exposure
- **Jumper VM pattern**: bridge between VPN and VMware LAN = strict network isolation
- **Runbook documentation** for every service: start, restart, troubleshoot

<Callout type="note" title="Why ESXi">
I hesitated with Proxmox (open source, more modern), but ESXi was already running on the existing hardware and the team didn't want to absorb a hypervisor migration alongside this overhaul. ESXi delivers on what it promises for this scope.
</Callout>

## Lessons

Three things I learned on this engagement:

1. **The jumper VM pattern is one of the cleanest ways to isolate an internal LAN.** Rather than NAT-ing the edge directly into the LAN, routing traffic through a dedicated VM that bridges VPN ↔ LAN gives you a clear boundary and a centralized filtering point. When something goes wrong on the network side, everything converges on that single chokepoint — easy to observe, easy to harden.
2. **Pritunl is underrated.** The web UI for managing OpenVPN + Pritunl Zero for internal SSO covers 80% of a small team's VPN/SSO needs without the complexity of Keycloak or Okta.
3. **The runbook beats the architecture.** Elegant but undocumented infra = single-person-dependency. Every service I set up has a one-page markdown with the basic commands. That's what let the team stay autonomous after I left.
